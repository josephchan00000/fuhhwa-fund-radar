# 依照 ponytail 整理程式（2026-10-31 規劃；排在 `docs/lab_signal_quality_plan.md` 那幾段之後）

> 使用者 2026-10-31：「都完成以後再幫我依照ponytail 如下網站：https://github.com/DietrichGebert/ponytail。的架構去整理我的專案中的程式碼，
> 記得絕不能影響到本來的功能，要詳細逐步執行。」

## 1. ponytail 是什麼

ponytail（GitHub `DietrichGebert/ponytail`，MIT 授權）**不是資料夾樣板，是一套給 AI 寫程式、整理程式的做法**：「最小、完整的改動」。重點：

- **寫之前的梯子**：先讀懂要改的程式和它牽動的地方，再依序問——需要存在嗎？專案裡已經有嗎？標準函式庫有嗎？已經裝的套件有嗎？一行寫得完嗎？最後才寫最少能用的程式。
- **保留現有結構**：沿用專案原本的分層、介面、慣例；不加沒人要的抽象、包裝、設定、「以後可能用到」的程式；刪掉比加上好。
- **絕不砍**：信任邊界的驗證、防止資料遺失的錯誤處理、安全、無障礙。
- **有分支、迴圈、解析、錢、安全的邏輯，留一個小測試**；有已知上限的捷徑，標註 `shortcut: <上限>, <什麼時候要升級>`。
- **整個專案的體檢（ponytail-audit）**：先畫地圖（說明文件、建置與部署設定、相依套件、入口、測試；預期負載；資料怎麼進來、存在哪、怎麼出去），
  再依「正確 → 安全 → 撐得住預期負載 → 有測試 → 速度 → 精簡」找問題。精簡包括：刪掉沒用到的、兩個做同一件事的留一個、標準函式庫已經有的、
  只有一個實作的抽象、該合併的近似複本、一個函式做好幾件不相干的事（依工作拆，不依行數拆）。
  每一條都要有具體案例（「這個輸入／情況會得到這個錯的結果」）；說某段沒用到之前，要全專案搜尋（含測試、設定、字串引用）；
  分「必修／該修／可以更好」，最多 20 條；**體檢只出報告、不改程式**。
- **債務帳（ponytail-debt）**：收集 `shortcut:` 註解成一份清單，避免「以後再說」變成「永遠不做」。

## 2. 套到這個專案

- **規模**（2026-10-31）：Python 344 支、約 11.3 萬行（`arm/` 1.7 萬、`arm/lab/` 8.1 萬、`scripts/` 1 萬）；測試 191 支、3.9 萬行；workflow 13 支（用到 44 支腳本）；排程 7 個。
- **預期負載**：一個人用的研究與儀表板網站＋每天幾班 CI。重點是**算對、資料不丟、CI 不壞、頁面不壞**，不是同時很多人用。
- **最要緊、先看的地方**：資料抓取與落檔（鐵則：非空的落檔絕不覆寫成空）、push 觸發的併檔通道（daily.yml、strategy_cands.yml）、
  研究與回測的計算（第一份規劃第 5 節的五道檢查是這一塊的安全網）、建頁。

## 3. 怎麼確保「絕不影響本來的功能」

1. **輸出完全相同檢查（最重要）**：整理前，用同一份資料建一次全部頁面（`dashboard/*.html`、`*.json`）與研究檔；整理後再建一次，逐位元比對（產生時間這類戳記除外）。
   有任何不同就停下來、退回，查清楚。只有在「本來就要修的錯」才會有差，而且要在報告裡寫明。
2. **路徑不動**：排程 prompt、workflow、CLAUDE.md、技能（`.claude/skills/`）、路徑規則（`.claude/rules/`）裡寫到的腳本與資料路徑，一律不改名、不搬家。
   排程 prompt 只能在它自己的視窗改；workflow 用的是「被推分支」上的檔。非搬不可就留舊路徑轉接，等所有引用都改好再拿掉。
3. **刪之前全專案搜尋**：程式、測試、workflow、排程 prompt（CLAUDE.md 原文①～⑦）、wiki、技能、字串與動態引用（例 `importlib`、`getattr`、`"scripts/xxx.py"` 字串）。
4. **一步一個小 PR**：全部測試＋`tests/test_plain.py`＋`tests/test_old_urls.py`＋輸出比對全過才合併；合併後看 CI 那一輪成功、資料日推進。
5. **不砍**驗證、錯誤處理、防呆（例：落檔不可覆寫成空、併檔通道的 JSON 驗證、資料過期標記）。
6. **不改任何研究的規格與結果**：整理程式不是改研究。

## 4. 分段（每段做完給你看，你說「繼續」才往下）

1. **地圖（只讀）**：入口清單（workflow 13、腳本 93、排程 7、技能、建頁）、每個入口用到哪些模組、資料從哪進來、寫到哪裡；
   找出沒有被任何入口或測試用到的程式；記下每一個寫檔的地方。
2. **體檢報告（不改程式）**：照 ponytail-audit 的六項，最多 20 條，分必修／該修／可以更好，每條寫「這是什麼、問題、怎麼修、不修會怎樣」與具體案例；
   附「可以減少幾行」。給你看，你挑要修哪幾條。
3. **逐條修**：你挑的一條一個 PR，照第 3 節驗證（輸出完全相同，或只差在要修的錯）。
4. **債務帳**：已知上限寫成 `shortcut:` 註解，整理成 `docs/code_debt.md`。
5. **知識庫**：改相關的頁、`wiki/log.md` 加一行。

## 5. 不做

- 不為了「看起來整齊」大搬家、改名（ponytail 本身就要求保留現有結構）。
- 不加新框架、新套件、新的抽象層。
- 不在別的工作裡順便整理（只在這幾段做）。
