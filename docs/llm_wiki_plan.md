## 2. Karpathy 的 LLM Wiki 是什麼

出處：Andrej Karpathy 2026-04 的 gist「LLM Wiki」。三層、三個動作：

- **原始資料（不改）**：這裡就是 `docs/*_plan.md`（約 45 份規劃與結果）、`reports/`、程式、git 歷史。
- **知識庫（我維護）**：`wiki/` 底下的 markdown，一頁一個主題、彼此連結；
  `wiki/index.md` 是目錄（每頁一行連結＋一句摘要，依類別分組），`wiki/log.md` 是日誌（只往後加，`## [日期] 動作 | 標題`）。
- **規則**：CLAUDE.md 寫知識庫怎麼用、怎麼維護。

三個動作：

- **收錄**：做完一件事，把學到的寫進對應的頁（改掉過時的句子、補連結），日誌加一行。不再往 CLAUDE.md 後面加。
- **查詢**：先看目錄，再讀相關的頁；你問的問題如果答案有保留價值，也寫回頁面。
- **整理**：找頁和頁之間互相矛盾、內容過時、沒有被連到、目錄漏列的地方。

規模：Karpathy 說幾百頁以內只靠目錄就找得到，不需要搜尋工具。這裡約 60 頁。

## 3. 目標樣子

### 3.1 CLAUDE.md 只留什麼（目標 2.5 萬字以內，現在的十二分之一）

1. **一段話**：這是什麼專案、主要資料夾（`arm/`、`scripts/`、`data/`、`dashboard/`、`reports/`、`docs/`、`wiki/`）。
2. **知識庫怎麼用**（約 10 行）：動手前先看目錄、讀相關頁；做完更新頁面與日誌；CLAUDE.md 只有鐵則或指令改了才動。
3. **目錄**：用 `@wiki/index.md` 一起載入（約 6～8 千字），所以每個對話都看得到有哪些頁、每頁講什麼。
4. **鐵則**（每次都要守，一條一句，約 30 條）。例：
   - 容器裡絕不跑資料抓取腳本（被擋、會空轉）；資料抓取交給 CI。
   - 時間一律台北時間（`arm/clock.py`、`TZ=Asia/Taipei`）。
   - 本機建出來的 `dashboard/*.html`、`*.json` 不 commit；`git add` 一律寫明路徑。
   - 不可宣稱「線上已生效」（容器看不到 Vercel）。
   - 規格先寫好、commit 之後才算結果；要改就升版本，不在看過結果之後改舊版本。
   - 禁用詞清單與唯一例外。
   - 主頁面用字規則（細節在頁裡）。
   - commit 一律 noreply 身分；不寫個人 email、本機路徑。
   - 子代理回報只要三行。
5. **四個指令**：標題一字不改（排程 prompt 指名引用「指令：全部更新」等標題），步驟寫精簡版、細節連到頁。
   排程 prompt 有指名的編號也保留：全部更新步驟 9⑤、9⑨，ETF 週掃步驟 2.5，「已知環境限制與防呆」的 -32003 條。
6. **新指令「整理知識庫」**（第 5 節）。

### 3.4 改程式時自動帶出對應的頁

Claude Code 有「路徑規則」：`.claude/rules/*.md` 開頭寫 `paths:`，我讀或改到符合的檔案時，那份規則才會自動載入。
用法：每個主題一份很短的規則（1～1.5 千字），只寫「改這幾支之前先讀 `wiki/lab/signals.md`」加上兩三條絕對不能破壞的事。例：

```
---
paths:
  - "arm/lab/sig*.py"
  - "scripts/run_sig.py"
---
改訊號判定之前先讀 wiki/lab/signals.md。
- 規格（sigspec.py）先改、先 commit，才重跑研究；升版要寫 RES_VER。
- 狀態型每一天一樣重（VER 22），不要改回每一段平均。
```

這是解決「搬出去之後我沒讀到」最有效的一道：不靠我記得去讀，碰到檔案就自動出現。約 15 份。

## 4. 怎麼搬，才不會漏

### 4.1 第一步：逐字搬（零改寫）

- 寫 `scripts/wiki_split.py`：一張對照表「CLAUDE.md 第幾行到第幾行 → 哪一頁」，套在指定 commit 的 CLAUDE.md 上。
  每一行只會落在一頁。
- 檢查：所有頁的內容依原順序接起來，要和原本的 CLAUDE.md 一字不差（只多頁首）。不符就不 commit。
- 同時寫新的精簡 CLAUDE.md、`wiki/index.md`、`wiki/log.md`。
- 這一步之後每個對話就只讀精簡版；頁面內容還是原樣（新舊混在一起），但什麼都沒少。

### 4.2 第二步：整理（每頁照 3.3 的格式重排）

- 現在的規則移到前面、歷史移到後面；過時的說法標出來（例：「配置頁」現在是「選股頁」）。
- 重複的說明合併：例如「生效條件＝merge 後排程搬家」22 處，集中在 `ops/routines.md` 寫一次，其他地方一句連結。
- 補頁和頁之間的連結；寫 `lessons.md`、`user.md`。
- **保證沒有丟掉事實**：`scripts/wiki_facts.py` 從原本的 CLAUDE.md 抽出所有「事實記號」——檔名與路徑、函式名、日期、帶單位或 % 的數字、
  使用者原話「…」、run／commit 編號、版本號——每一個都要還出現在 `wiki/` 或新的 CLAUDE.md 裡。
  真的要刪的（已經不成立的），要在日誌寫一行刪了什麼、為什麼。

### 4.3 git 歷史

舊的 CLAUDE.md 永遠留在 git 歷史，日誌第一行記下搬家前最後一個 commit 編號，要對照隨時拿得到。

## 5. 之後怎麼維護

- **做完事**：更新相關頁（改掉過時的句子，不是往後加），日誌加一行，摘要變了就改目錄那一行。
  CLAUDE.md 只有鐵則或指令改了才動。
- **你問問題**：答案值得留就寫回頁面（例如「為什麼新飆股放 8 格」寫進 `boom-live.md`）。
- **新指令「整理知識庫」**：跑 `scripts/wiki_lint.py`（連結、目錄漏列、沒有被連到的頁、提到的檔案與函式還在不在、頁太長、CLAUDE.md 太長），
  我再讀一遍找互相矛盾和過時的地方，修好、日誌記一行、回報。
- **測試** `tests/test_wiki.py`（每次 pytest 都跑）：
  - CLAUDE.md 不超過 3 萬字（防止又長回去）；每頁不超過 1.5 萬字；目錄不超過 1 萬字。
  - 每一頁都在目錄裡；目錄的每個連結都存在；頁面內的相對連結都對得到。
  - 排程 prompt 指名的標題與編號還在 CLAUDE.md（「指令：全部更新」、步驟 9⑤、9⑨、週掃 2.5、-32003 條…）。
  - 程式註解裡寫「見 CLAUDE.md 某段」的，那段要還在，或已改成指向 wiki 頁。
  - 個資檢查（`tests/test_privacy.py` 本來就涵蓋整個 repo 的文件）。
- **你怎麼看**：repo 是公開的，在 GitHub 上點 `wiki/index.md` 就能一頁頁點著讀（Vercel 只發布 `dashboard/`，知識庫不會出現在網站上）。

## 8. 風險與對策

| 風險 | 對策 |
|---|---|
| 搬出去之後我沒讀到，又踩一樣的坑 | 鐵則留在 CLAUDE.md；目錄常駐；改程式時路徑規則自動帶出；指令標題保留 |
| 搬的時候漏掉東西 | 先逐字搬＋一字不差的檢查；整理時用事實清單比對；舊版留在 git 歷史 |
| 頁面和程式慢慢對不上 | 「整理知識庫」檢查頁面提到的檔案、函式還在；做完事就改頁 |
| CLAUDE.md 和頁面各寫一份、後來不一致 | CLAUDE.md 只放鐵則與指向，不放細節 |
| 頁越來越多找不到 | 目錄每頁一句摘要；超過約 150 頁再考慮加搜尋工具 |
