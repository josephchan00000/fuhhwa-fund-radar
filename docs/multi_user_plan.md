# 復華基金雷達 · 100–300 人使用規劃

> 狀態：**待使用者確認後執行**（2026-08-14 產出）。
> 本文件盤點多人使用會遇到的狀況，並依「穩定／流暢／正確」規劃對策。確認後依 Phase 1 → 2 順序執行。

## 結論先講

現在的架構（CI 產靜態 HTML → Vercel CDN）**天生就是對的多人架構**：使用者端零後端、零資料庫、零登入狀態，所有人讀同一份 CDN 快取的靜態頁，300 人與 3 人的伺服器負載幾乎沒有差別。**不需要重構。**

要做的是把「單人時代可以人工吃掉」的邊界風險自動化——壞頁上線、部署漏接、線上停舊版這三類事故，過去靠你自己發現就好；300 人時任何一次事故都被放大百倍，必須改成「系統自己發現、自己叫」。

### 現況關鍵數字（2026-08-14 實測）

| 項目 | 數值 | 意義 |
|---|---|---|
| 頁面大小 | 789 KB（gzip 傳輸 **154 KB**） | 4G 手機初載約 1 秒級 |
| 外部資產依賴 | **0**（無外部字型/JS/CSS，連結皆為出站超連結） | 第三方故障面＝零 |
| 最壞情況月頻寬 | 300 人 × 3 次/日 × 30 日 × 154KB ≈ **4.2 GB** | 僅 Vercel 免費額度 100GB 的 ~4%，頻寬完全不是問題 |
| 後端／資料庫 | 無 | 零併發寫入問題；唯一寫入者是 CI |
| 已有防護 | workflow concurrency＋rebase 重試、factcheck 數字核對、過期紅章、免責聲明、noindex | 正確性基礎已投資很深 |

## 二、執行方案

### Phase 1｜程式端硬化（零費用；確認後直接執行；逐項獨立 commit、可獨立回退）

1. **快取改 `no-cache`（兩支 vercel.json 同步改：根目錄＋dashboard/）**
   - 行為：瀏覽器**每次仍必須向伺服器確認版本**（revalidate），內容沒變回 304（~1KB）、變了才全量下載。
   - 正確性性質不變：「看到舊的＝沒部署、不是快取」這條診斷鐵則依然成立（因為每次都 revalidate）；執行時同步更新 CLAUDE.md 該條註記。
   - 附驗證：部署後由 CI `curl` 兩連發（第二發帶 `If-None-Match`）確認 ETag／304 生效；若 Vercel 未回 ETag，退回 no-store（不會比現在差）。
2. **CI 煙霧測試（建表後、commit 前）**
   - 在 Actions 內以 headless Chromium 開建好的 `dashboard/index.html`：console 零錯誤＋關鍵區塊存在（#overview／#etfwatch／新聞區）＋今日日期標記＋內嵌 `__EH` JSON 可解析。
   - 紅 → 該輪**不 commit、不部署**（線上維持前一版＝天然 last-known-good），run ❌ 寄 failure 信。
   - 定位＝擋「結構性壞頁」；數字內容仍走 factcheck「不擋發佈、紅章警示」——與既有「防線不可硬到什麼都沒更新」原則不衝突。
   - 成本：Playwright 瀏覽器經 actions/cache 快取後每班約 +30–60 秒。
3. **部署後線上驗證（根治 2026-08-13 型事故的發現延遲）**
   - 打完 Deploy Hook 後，CI 輪詢正式網址（**Actions 的網路可達 vercel.app**，與被 proxy 擋的容器不同），等「產表時戳＝本輪」出現在線上頁；逾 ~5 分鐘 → run ❌ 寄信。
   - 三支 workflow（daily／afterhours_refresh／etf_holdings）共用同一步；afterhours 與 etf_holdings 的守門條件（資料沒變就跳過）照舊。
   - 效果：「資料進 main、線上停舊版」從「使用者隔天發現」變「幾分鐘內自動警報」。
4. **Uptime 哨兵 workflow**
   - 每 30 分 schedule：curl 線上頁驗 HTTP 200＋建表時戳落在 48 小時內＋關鍵內容標記；**連兩次**失敗才 ❌ 寄信（吸收單次網路抖動；GitHub cron 遲到特性對巡邏用途無妨）。
   - 選配：外部 UptimeRobot（免費、5 分鐘粒度、不依賴 GitHub 自身），雙保險。
5. **長開分頁提示**
   - 頁面 JS 每 30 分自查「本頁載入至今」時長，逾 6 小時顯示細條「本頁載入已久，資料可能已更新——請重新整理」；復用既有 warn() 橫幅機制。
   - 搭配第 1 項可進階：同源 HEAD 比對 ETag，「偵測到新版」才顯示。**不自動 reload**（避免打斷閱讀）。
6. **（選配）頁尾回報管道**：mailto 或表單連結——300 人的「壞了跟誰說」。

### Phase 2｜帳號與治理（需要你決策／動 Vercel 後台，約 10 分鐘）

- **A. Vercel 方案**：Hobby 條款**明文禁止商業用途**——若本站屬公司內部／任何商業性質，應升 **Pro（US$20/月/席）**；被停權＝全站即刻消失，這是目前最大的帳號單點風險。純個人非商用可留 Hobby（流量僅用到額度 ~4%）。
- **B. 存取控制（三選一）**：
  1. 維持公開＋noindex（現狀）——最簡單；本站資料皆屬公開資訊，通常足夠。
  2. Vercel Pro 的 Password Protection（全站共用一組密碼）——「半私有」最低成本做法。
  3. 名單制 SSO（如 Cloudflare Access）——300 人超過免費額（50 席），約 $3/人/月量級；除非資料敏感，**不建議**。
- **C.（選配）自訂網域**：好記好轉傳，Vercel 免費掛。
- **D. 用量可見性**：開 Vercel Web Analytics（後台開關即用）——知道真實 DAU／尖峰分布，之後所有效能決策有數字依據。
- **E.（選配）DR 鏡像**：CI 同步部署 gh-pages 備援網址；平時不公布（避免兩個網址混淆），Vercel 全掛時才啟用。

### Phase 3｜觀察名單（現在不做）

- 頁面瘦身／資料拆檔：gzip 超過 500KB 再議（現 154KB）。
- repo 歷史膨脹：每日多筆 commit 各寫入 ~800KB HTML，一年後 clone 才會有感；CI 已 shallow checkout，影響有限。屆時再議歷史治理。
- workflow 錯峰微調：現有 concurrency＋rebase 重試已吸收；出現實際互搶紀錄再動。

## 三、明確不建議做的事（防過度工程）

- ✗ **改成後端 API／資料庫／SSR**——把「零併發、零狀態、CDN 天生扛量」的最大優勢丟掉，換來伺服器、連線數、快取一致性一整包新故障面；300 人規模完全不需要。
- ✗ **把資料拆成多支 fetch 載入**——引入「部分載入失敗」中間態；現在單一 HTML 要嘛全新要嘛全舊，狀態最乾淨。
- ✗ **長 max-age 快取**——會回到「線上停舊版」惡夢；no-cache＋ETag 已同時拿到正確與省流。
- ✗ **為尖峰做壓測／擴容**——靜態 CDN 對 300 人尖峰是零負載題。

## 四、成本與工作量

| 項目 | 費用 | 工作量 |
|---|---|---|
| Phase 1（六項） | $0 | CI 每班 +1~2 分鐘；一個工作階段內完成 |
| Phase 2 | $0～20/月（視 A/B 決策） | 你動 Vercel 後台約 10 分鐘 |
| 維運心智負擔 | — | 新增的全是「壞了會自己叫」的哨兵，**不新增任何例行人工步驟** |

## 五、請你確認的決策點

1. **Phase 1 六項全做？**（建議：全做；第 6 項回報管道可先略）
2. **網站用途屬性**：公司內部／商用 → 升 Pro？還是個人非商用留 Hobby？
3. **存取控制要哪一級？**（建議：資料皆公開資訊 → 維持現狀 noindex；要「半私有」→ Pro 密碼保護）
4. **監控警報**：GitHub failure 信寄 repo 擁有者（現有模式）夠嗎？要不要加 UptimeRobot 外部監控？
