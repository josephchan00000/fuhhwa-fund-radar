## 結論先講

現行架構（CI 產靜態 HTML → Vercel CDN）天生就是對的多人架構，**不需要重構**。逐項評估後，真正「必要」的只有兩件半：**對時哨兵（③④合併）**、**煙霧測試（②，兩段式上線）**、加上順手做的**頁齡提示（⑤）**。其餘不是「划算但非必要」就是「視用途而定」，還有三項在成本攤開後應該砍掉。

### 評估基準的關鍵事實（2026-08-14 實測）

| 事實 | 數值 | 對評估的影響 |
|---|---|---|
| repo 屬性 | **私有** | GitHub Actions 免費額＝**2,000 分鐘/月**，超額 $0.008/分——新增 CI 步驟都要算這筆帳 |
| 目前 CI 用量 | 平日 ~34 分/日 ≈ **~1,000 分/月（已用 50%）** | 三支 workflow 平均每輪 2.0~2.6 分、每日 ~15 輪 |
| 頁面 | 789KB／gzip **154KB**，零外部資產 | 頻寬與尖峰完全不是問題（月最壞 4.2GB＝免費額 4%） |
| repo 大小 | ~14MB（上線 6 週） | 歷史膨脹尚早，觀察即可 |
| 事故史 | 6 週內：結構性壞版上線 ~2 次、部署漏接 2 次，**全部靠人工發現** | 「必要性」的依據——這類事故在 300 人時代價放大百倍 |

## 一、情境盤點（同 v1，摘要）

- 穩定：S1 壞頁上線（高）、S2 部署漏接（高，08-13 實例）、S3 掛了沒人知道（高）、S4 Actions 全停（中，靜態頁天生兜底）、S5 Vercel 故障（低）、S6 Hobby 禁商用（高*）、S7 workflow 互撞（已解）。
- 流暢：P1 no-store 每次全載（中）、P2 尖峰（無風險）、P3 手機（良好）、P4 頁面長大（觀察）。
- 正確：C1 長開分頁舊資料（中）、C2 「main 有了≠線上有了」盲區（高）、C3 數字錯放大（factcheck 已投資很深，維持）、C4 合規（已有免責/來源/禁用詞）、C5 誰能看（依需求）。

## 二、必要性 × 額外成本逐項評估（v2 核心）

「不做的風險」以本 repo 的真實事故史為據，不憑空想像；「持續成本」含金錢、CI 分鐘、維護心力、誤報、副作用五種。

### Phase 1 各項

| 項 | 不做會怎樣（史實依據） | 一次成本 | 持續成本 | 判定 |
|---|---|---|---|---|
| ③④ **對時哨兵**（合併修正版：掛既有班次尾端，比對線上頁時戳 vs main） | 「資料進 main、線上停舊版」「掛了沒人知道」都要等使用者回報——08-13 實例隔天才發現；「靜默失敗」是本專案文件記載最多的事故類 | 低（一個步驟掛三支 workflow） | **+~50–100 CI 分/月**；誤報率低（45 分寬限）；殘餘盲區＝深夜（無部署時段，可接受） | **A 必要**，全部裡 CP 值最高 |
| ② **煙霧測試**（headless Chromium 驗建表產物；兩段式上線） | 結構性壞版直達 300 人。史實：07-31 新聞卡內容整片消失（連三回合上線）、07-31 按鈕全失效——都是上線後被人發現 | 中（~100 行測試碼） | **+~135 CI 分/月**（只掛 daily.yml 主班；另兩支用輕量標記檢查≈0）；測試碼要跟版面演進；**誤報會擋掉整班更新**→先「只告警」1–2 週，誤報歸零才開攔截 | **A 必要**，但攔截權要有試用期 |

| UptimeRobot 外部監控 | GitHub 自身掛掉時的獨立第三隻眼 | 低（你要註冊帳號、設 2 個監測） | $0（免費版 5 分粒度、50 個監測）；只驗「活著＋關鍵字」、驗不了新鮮度 | **C+ 選配**，與哨兵互補不重疊 |

## 三、執行方案（修正版）

### Phase 1（確認後執行；逐項獨立 commit 可回退）

1. **對時哨兵（原③＋④合併）**：三支 workflow 尾端各加一步——curl 線上頁，驗 HTTP 200＋線上「產表時戳」與 origin/main 一致（45 分寬限）；不符→run ❌ 寄 failure 信。每日約 10–15 個檢查點、全落在部署後的關鍵時刻，**不新增任何 runner 啟動**。全 pipeline 死透的極端情境由既有 Routine 推播鏈＋瀏覽器端逾期橫幅兜底。
2. **煙霧測試（兩段式）**：daily.yml 建表後 headless Chromium 驗 console 零錯誤＋關鍵區塊＋今日日期＋內嵌 JSON 可解析。**第 1–2 週只告警不攔截**，誤報歸零後改為「紅→不 commit 不部署（線上維持前一版）」。afterhours/etf_holdings 兩支用零成本的輕量標記檢查（關鍵 class/日期 grep）。
3. **頁齡提示**：頁面 JS 每 30 分自查載入時長，逾 6 小時顯示「本頁載入已久，資料可能已更新」細條；復用既有橫幅機制、不自動 reload。
4. **快取 no-cache＋ETag**：兩支 vercel.json 同步改；部署後 curl 兩連發驗 304；同步更新 CLAUDE.md「看到舊的＝沒部署」註記（該性質不變，每次仍 revalidate）。
5. **（選配）UptimeRobot**：你註冊、我提供監測設定值。
6. **（選配）頁尾回報管道 mailto。**

### Phase 2（需你決策）

- **A. 用途屬性**：商用→升 Pro；個人→留 Hobby。（替代案 Cloudflare Pages 僅在「商用且不想付費」時再議，遷移成本與風險見上表。）
- **B. 存取控制**：建議維持公開＋noindex。
- **C. 自訂網域**：純偏好。

### Phase 3（觀察名單，設好閾值再議）

頁面 gzip >500KB 才議瘦身；repo >100MB 或 CI checkout 明顯變慢才議歷史治理。

## 四、明確不建議做的事（v2 擴充）

- ✗ 改後端 API／資料庫／SSR——丟掉零併發、零狀態、CDN 天生扛量的最大優勢
- ✗ 資料拆多支 fetch——引入「部分載入失敗」中間態
- ✗ 長 max-age 快取——回到「線上停舊版」惡夢
- ✗ 為尖峰壓測／擴容——靜態 CDN 對 300 人是零負載題
- ✗ 獨立 30 分 cron 哨兵——+1,440 分/月吃掉七成 Actions 免費額（v2 修正）
- ✗ 第三方 Analytics script——免費額不夠用＋破壞零外部依賴（v2 修正）
- ✗ DR 鏡像常備——機率×影響不划算，留 runbook 即可（v2 修正）
- ✗ 名單制 SSO／300 人共用密碼——前者貴（~$900/月）、後者是安全劇場

## 五、決策點結果（2026-08-14 定案）

1. **核心組合**：✅ 已實作於分支（見頂部狀態），待 merge 進 main 生效。
2. **用途屬性＝家人分享約 30 人、非商用** → **維持 Vercel Hobby，不升 Pro**（定案）。
   **「多人讀取不產生額外成本」的架構理由**（使用者提問，記於此供日後參照）：
   ①**GitHub Actions 分鐘完全不隨人數變動**——CI 按排程跑，1 人看與 300 人看次數相同；
   ②**資料來源站（證交所／期交所／etfinfo／鉅亨）只有 CI 會碰**，使用者永遠不碰 →
     人數再多也不會有「請求爆量被封鎖」的風險；
   ③**唯一隨人數增加的是 Vercel 頻寬**：頁面是單一自包 HTML（零外部資產、零 API 呼叫），
     30 人約 0.42GB/月＝免費額 100GB 的 **0.4%**（300 人也只有 4%）；no-cache＋ETag 讓
     重複造訪多回 304（~1KB），實際更低。請求數約 5,000/月 vs 100 萬額度。
3. **UptimeRobot**：暫緩（哨兵已覆蓋主要情境，日後要 5 分鐘粒度再加）。
4. **回報管道 mailto**：先略（內部使用者會直接找維護者）。
